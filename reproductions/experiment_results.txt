Demo 3 — TAP 状态机自检 (转移表 = 本实验 KAT 锚点)
========================================================================

-- 任意状态连续 5 个 TMS=1 必达 Test-Logic-Reset

Demo 1 — DR 扫描枚举 IDCODE (识别链上器件)
========================================================================
    链上器件(TDO 侧在前):
      [0] CPLD-协处理
          IDCODE=0x0ABCD093  version=0x0 part=0xABCD mfr=0x49 bit0=1
      [1] MCU-主控 (示例: Cortex-M)
          IDCODE=0x40BA08F7  version=0x4 part=0x0BA0 mfr=0x47b bit0=1
    [PASS] 两个 IDCODE 的 bit0 均为 1 (标准强制,也是"该器件支持 IDCODE"的判据)
    [PASS] 读回值与仿真链定义一致(先出 TDO 侧器件)
    [PASS] 主控 part number 0x0BA0 = ARM CoreSight DP 的典型值(示例器件)

========================================================================
Demo 2 — 全 1 指令(BYPASS)测链长 (不知道型号也能数器件)
========================================================================
    [PASS] Update-IR 后两颗器件 IR 均为全 1 (= BYPASS, 标准规定)
    Capture-IR 固定模式回读(低 2 位须 01): 主控=[0001] CPLD=[00000001]
    [PASS] 主控 Capture-IR 低 2 位 = 01 (标准要求,可用于测 IR 长度)
    标记位在第 3 个 TCK 从 TDO 出现 → 链长 = 2 颗器件(每颗 BYPASS 贡献 1 bit)
    [PASS] BYPASS 链长 = 2 (= 器件数)

Node v24.16.0 | 零依赖 | 确定性输出

========================================================================
KAT — AN3155 校验规则(实验的规范锚点)
========================================================================
    [PASS] 8 个命令字与其校验字节构成按位取反对 (0x11↔0xEE 等)
    [PASS] 地址 0x0000ABCD 的 XOR 校验 = 0x66 (3 字节异或规则)
    [PASS] 同步字节 0x7F → ACK 0x79
    [PASS] 命令校验错误 → 双 NACK 0x1F

========================================================================
Demo 1-2 — 同步 / Get / GetID / Read Memory(未保护器件)
========================================================================
    Get       → ACK; bootloader v0x31; 支持命令: 00 02 11 21 31 43 82 92
    [PASS] Get 返回版本 0x31 与命令表 (ACK...ACK 帧)
    GetID     → ACK; PID = 0x0466
    [PASS] GetID 帧结构 = ACK,len,PID_hi,PID_lo,ACK
    Read @0x000000(flash 别名窗口) × 64B:
      79 40 00 00 20 09 10 00 08 53 45 43 52 45 54 3D ...
      其中发现字符串: "SECRET=Tr0ub4dor&3 (device key)"
    [PASS] 读回固件头 (SP=0x20000040, Reset=0x08001009)
    [PASS] 固件内明文密钥被完整提取 (未保护 = 全裸)

========================================================================
Demo 3 — Readout Protect (0x82): 读保护生效
========================================================================
    Readout Protect → 79 79 (ACK + 擦除完成 ACK), 全片已被擦除, RDP=1
    [PASS] RDP 置位命令返回双 ACK
    [PASS] 置位过程伴随全片擦除 (密钥此时就已不存在于 flash)
    [PASS] 诊断命令 Get 仍可用 (bootloader 本身不锁)
    Read Memory @RDP1 → 1F (NACK)
    [PASS] RDP=1 时 Read Memory 被拒 (0x1F) —— 协议层防线成立
    [PASS] RDP=1 时 Write Memory 同样被拒

========================================================================
Demo 4 — Readout Unprotect (0x92): 降级的代价
========================================================================
    Readout Unprotect → 79 79, RDP=0, flash 全 0xFF
    [PASS] 降级命令本身成功 (ACK×2)
    [PASS] 降级后能读, 但只剩 0xFF: 原固件已随降级擦除
    → 正常路径下 RDP1→RDP0 不是绕过: 厂商用"自毁"换"保密"

========================================================================
Demo 5 — 电压毛刺跳过 RDP 检查(机理级模型,非电路仿真)
========================================================================
    同样 RDP=1, 但 RDP 比较被毛刺跳过:
      Read → ACK + 数据, 字符串 "SECRET=Tr0ub4dor&3 (device key)"
    [PASS] 毛刺命中时受保护固件完整外泄
    [PASS] 对照: 同一时刻未毛刺的器件仍拒绝 (毛刺是时序窗口, 不是开关)
    → 现实中: WOOT'20 用电压毛刺+FPB 在真芯片上实现了这一点;
      picopwner 把成本降到一只树莓派 Pico; 详见 knowledge/01 #3/#22

========================================================================
总结
========================================================================
    通过 17 项, 失败 0 项

    攻击含义(对照 knowledge/01 / 02):
    * 不到 20 元的 USB-TTL + AN3155 协议 = 未保护 STM32 的完整固件提取器
    * RDP1 挡住的是"协议层", 挡不住"物理层"(毛刺打比较指令)
    * RDP 降级即自毁 —— 所以真实攻击都瞄准"检查的执行"而非"标志位"
    * 防御对照: RDP2(不可逆)/flash 加密 + 密钥在 eFuse, 见 knowledge/03 #14

CAN / ISO-TP / UDS 攻击仿真 (ISO 11898 / 15765-2 / 14229)

========================================================================
KAT — 协议常量锚点
========================================================================
    [PASS] SF: 2 字节负载 → [0x02, 0x10, 0x03] (高位 nibble=0)
    [PASS] FF: 40B 负载 → [0x10, 0x28, ...6B] + 5×CF (12-bit 长度域)
    [PASS] CF: 序号从 1 起, 0x21,0x22,...,0x25 (4-bit 滚动计数)
    [PASS] UDS 响应 SID = 请求+0x40 (0x10→0x50, 0x27→0x67, 0x22→0x62)
    [PASS] NRC: 0x33 security access denied / 0x35 invalid key / 0x7E not supported in session
    [PASS] bus-off 判据: TEC 超过 255 → 32 次错误 × +8 = 256 (恰好越界)

========================================================================
Demo 1 — CAN 仲裁: 低 ID 赢 (无认证广播总线的根源性质)
========================================================================
    同拍竞争: 动力 ECU(0x100), 仪表 ECU(0x1A0), 诊断仪(0x7DF)
    仲裁胜者: 动力 ECU (0x100) —— ID 数值最小者
    [PASS] 数值最小 ID 获得总线 (0x100 < 0x1A0 < 0x7DF)
    → 攻击含义: 持续发 0x000 等极低优先级帧 = 让所有正常报文永远排队 (泛洪 DoS)

========================================================================
Demo 2 — bus-off 攻击 (Cho & Shin, CCS 2016): 选择性踢 ECU 下线
========================================================================
    攻击模型: 每轮让受害者的发送产生一次错误 (TEC+8)
    1: TEC=8; 2: TEC=16; 3: TEC=24 ...
    第 31 轮: TEC=248 (error-passive, 还在线); 第 32 轮: 32: TEC=256 → 超过 255, bus-off!
    [PASS] 仪表 ECU 经 32 次错误被驱逐下线 (TEC=256 > 255)
    [PASS] 旁观的另一 ECU 不受影响 (选择性 DoS)——攻击只针对 0x1A0
    [PASS] 攻击者自己也 bus-off 1 次但立即复位 ("无所谓"的对手模型, 见 04 域 #6/#9)
    → 防御对照: SecOC 的 MAC 挡不住这里 (bus-off 是链路层机制); 检测靠 ECU 指纹/错误计数监控 (04 域 #7)

========================================================================
Demo 3 — ISO-TP 分帧往返 (UDS 的传输层)
========================================================================
    请求 10 03 → 1 个 SF: 02 10 03
    23B 响应 → 4 帧: FF=10 17 62 F1... CF=21,22,...
    [PASS] 接收方在 FF 后回 FlowControl [0x30, BS, STmin]
    [PASS] 分帧重组后与原负载逐字节一致

========================================================================
Demo 4 — UDS 合法流程: 会话 → SecurityAccess → 读 DID
========================================================================
    默认会话直接读 DID F15A → 7F 22 7E (NRC 0x7E)
    [PASS] 默认会话不支持 → NRC 0x7E (会话是第一道门)
    进扩展会话 → 50 03 00 19 01 F4
    [PASS] 0x10 03 → 0x50 03 (肯定响应+P2/P2*时序参数)
    请求种子 → 67 01 75 43 27 77 (seed=0x75432777)
    [PASS] 0x27 01 → 0x67 01 + 4 字节种子
    错误 key 0xDEADBEEF → 7F 27 35 (NRC 0x35)
    [PASS] 错误密钥 → NRC 0x35 invalid key
    正确 key 0xF19BCE91 → 67 02 (解锁)
    [PASS] 0x27 02 → 0x67 02, 安全访问通过
    读 DID F15A → 62 F1 5A 43 41 4C 5F 53... ("CAL_SECRET=0xDEADBEEF")
    [PASS] 解锁后敏感标定数据可读 (正常流程的终点)

========================================================================
Demo 5 — 攻击场景 A/B/C/D
========================================================================

-- A. 未认证直接读 (协议防线成立)
    跳过 0x27 直接读 → 7F 22 33 (NRC 0x33)
    [PASS] 未解锁 → NRC 0x33: 协议层把门外汉挡住了

-- B. 固件逆向提取 seed-key 算法 → 认证形同虚设
    用恢复的算法对种子 0x75432777 算 key → 67 02 → 读 → 62 F1 5A 43 41 4C 5F 53...
    [PASS] 算法一旦泄露, 0x27 完全失效 (安全性=算法保密性, 不是密码学)
    → 这就是 CANdid'24 / 历代 UDS 研究盯住 seed-key 的原因 (05 域 #4)

-- C. ECU 复位后种子重复 → 重放旧 key
    会话1: 种子=75 43 27 77, 合法 key 已记录 (如被嗅探/曾短暂解锁)
    复位后: 种子=75 43 27 77 (与上次完全相同!)
    [PASS] 弱 PRNG 固定初始状态 → 复位后种子重复
    [PASS] 重放会话1 的 key 直接解锁 (无需知道算法, 只需记录)
    [PASS] → 敏感 DID 再次可读: "拔插一下保险丝"就复现的攻击

-- D. 功能寻址广播 → 枚举全网关 ECU
    向功能寻址地址 0x7DF 广播 [10 03] (进扩展会话):
      0x7E8 网关 → 50 03 00 19 01 F4 (0x50)
      0x7EA 车身 → 50 03 00 19 01 F4 (0x50)
      0x7EC 车机 → 50 03 00 19 01 F4 (0x50)
    [PASS] 一条广播报文让 3 个 ECU 应答 → 诊断拓扑零成本枚举
    → 攻击链: 0x7DF 枚举 → 逐个试 0x27/0x22 → 找到没锁门的 ECU (B/C 场景的入口)

========================================================================
总结
========================================================================
    通过 24 项, 失败 0 项

    攻击含义(对照 knowledge/04 / 05):
    * CAN 的三大根源性质: 无认证广播 + 低ID仲裁 + 错误计数器 → 注入/饥饿/bus-off
    * UDS 的安全性依赖 "算法保密 + 种子管理", 两者都会在工程里出错
    * 复位重放(B/C 类)不需要任何密码学突破 —— 只要种子重复
    * 防御对照: SecOC(报文认证)/0x29(服务认证)/IDS(ECU 指纹), 见 04 域 #14 / 05 域方法地图
